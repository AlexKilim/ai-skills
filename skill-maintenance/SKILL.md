---
name: skill-maintenance
description: Review skill instructions in use or during revision. Propose evidence-based updates to skills, preferences and shared components when a practice is outdated, redundant, conflicting or a better fit is available.
---

When loading any skill, briefly check the instructions you will use. When revising one, read its full SKILL.md and check affected references. Apply this review to skill-maintenance itself. Ask what decision or failure each questionable instruction affects:

- For a possibly outdated requirement, verify the relevant version or workflow. Narrow the rule to the versions that still need it, or propose retiring it when its original constraint is gone.
- For obvious or repeated advice, identify what an agent would do differently without the sentence. Propose deletion or consolidation when the outcome is the same. Preserve exceptions and project constraints that are easy to miss.
- For a conflict, show the two instructions and a case where both apply but require different actions. Propose a scope or precedence that resolves it and ask the user to settle any ambiguity.

Use evidence already encountered during the task. Notice recurring problems, user corrections and successful solutions with a concrete second use. If nothing merits a change, continue quietly. Keep isolated observations in the conversation.

Consult the [preferred skills list](references/preferred-skills.md) when selecting skills for a nontrivial task or reviewing preferences. Reconsider an entry or shared component when it overlaps another, is superseded, or a better fit emerges. Use current primary sources or a small comparison to establish the benefit, compatibility and trade-offs. Popularity can help identify candidates.

Keep adoption for the current task separate from a change to shared defaults. Batch concrete proposals with their destination, wording or component change, and reason. Ask for confirmation before editing skills, the preferred list, or shared libraries, and offer GitHub publication in the same question. Continue independent project work while awaiting a decision.

Apply the approved items to their maintained source. Verify the original case, a nearby case outside the rule, and the installed copy. Publish when authorized and verify the remote revision. Offer publication once per batch. When the user chooses local-only, report the local result and respect that choice until the user reopens it. One confirmation can cover both the edit and the push.
