# file-edit

Как надёжно менять файлы пользователя — особенно на его компьютере через мост
(`device_list_dir` → `device_stage_files` → правка копии → `device_commit_files`).
Каждое правило ниже закрывает реальный сбой, который уже случался.

## Главные риски и почему они важны

| Риск | Что происходило | Защита |
|---|---|---|
| Коммит записал **старую** версию и вернул `written` | Повторный коммит из того же `stagedPath`, что и в прошлый раз, ушёл с устаревшим содержимым — правка «пропала», а я доложил об успехе | Каждый коммит — из **нового уникального** пути; после коммита — проверка |
| Staged-копия показывает старое содержимое | Сразу после `device_stage_files` файл в uploads ещё прежний | Сверить размер с `device_list_dir`, при расхождении подождать и перечитать |
| Пользователь правит файлы между ходами | Работа по вчерашней копии перетёрла бы его правки | Перед каждой новой правкой — свежий stage, `expectedMtimeMs` из него |
| Порча кодировки/переводов строк | Файлы в CP1251 и CRLF; Edit/Write работают как с UTF-8 | Побайтовый патч через latin-1, сохранение CRLF |
| Фрагмент не найден / найден не там | Число табов отличалось; неидемпотентный патч, запущенный повторно | Строгое «ровно N вхождений», `cat -A`, всегда патчить от свежей копии |
| Новая проверка ломает существующие вызовы | Добавил assert на размер и сам же передал больший размер | Новое ограничение → проверить все места вызова против него |

## Порядок работы

### 1. Получить актуальное состояние
- `device_list_dir` по нужной папке: размеры и `mtimeMs`.
- `device_stage_files` для всех файлов, которые будут меняться — **в этом ходе**, даже если они уже копировались раньше. Пользователь мог их поменять.
- Сверить размер staged-копии (`wc -c`) с `size` из листинга. Не совпало → `sleep 2` и перечитать; не помогло → stage ещё раз.
- Посмотреть кодировку и переводы строк: `file <f>`, `grep -c $'\r$' <f>` vs `wc -l <f>`.
- Если в staged-копии видны чужие изменения по сравнению с тем, что ты писал раньше, — это правки пользователя. Сохраняй их, работай поверх.

Если доступен рабочий `device_bash`, правь файлы прямо на компьютере им (тот же побайтовый подход), а stage/commit не нужен. Проверка после записи всё равно обязательна.

### 2. Согласовать изменение
- Следуй предпочтениям пользователя: если он просит подтверждение перед правкой — покажи точный diff/фрагмент и жди «да».
- Минимальный diff в текущем стиле файла, если не просили иного.
- Не угадывай содержимое файлов вне доступных папок (сигнатуры, заголовки). Скажи, какой файл нужен, и попроси положить его или вставить фрагмент.
- Меняешь сигнатуру/добавляешь ограничение (assert, `static_assert`, проверку размера) → найди **все** вызовы в доступной области (`grep -rn`) и проверь каждый против нового правила. О вызовах вне доступной области скажи явно.

### 3. Править копию побайтово
- Рабочая копия: `cp` staged-файла в **новую** папку вида `/mnt/user-data/outputs/<task>-<YYYYMMDD-HHMMSS>/`. Никогда не переиспользуй путь, из которого уже коммитил.
- Для файлов не в UTF-8 или с CRLF не используй Edit/Write — применяй скрипт ниже (latin-1 round-trip сохраняет любые байты, LF в шаблонах автоматически превращается в CRLF).
- Каждая замена проверяет число вхождений. Если шаблон не найден — смотри `cat -A` / `sed -n 'a,bp'` на точные табы и пробелы; хвостовые пробелы не включай в шаблон.
- Упала одна замена из нескольких → не перезапускай на уже частично изменённом файле: заново скопируй staged-исходник и примени весь набор.
- Покажи себе `diff --strip-trailing-cr <staged> <new>` (для CP1251 — через `iconv -f cp1251 -t utf-8`) и убедись, что изменилось только задуманное.

```python
#!/usr/bin/env python3
# bytepatch.py SRC DST SPEC.json
# SPEC: [["old", "new", count], ...]  (count = expected occurrences, usually 1)
# Byte-exact: any encoding kept; LF in patterns -> CRLF if the file uses CRLF.
import json, sys
src, dst, spec = sys.argv[1:4]
s = open(src, 'rb').read().decode('latin-1')
crlf = '\r\n' in s
for old, new, count in json.load(open(spec, encoding='utf-8')):
    if crlf:
        old, new = old.replace('\n', '\r\n'), new.replace('\n', '\r\n')
    n = s.count(old)
    if n != count:
        sys.exit(f'pattern found {n} times, expected {count}:\n{old!r}')
    s = s.replace(old, new)
open(dst, 'wb').write(s.encode('latin-1'))
print('ok', dst)
```

Шаблоны с не-ASCII текстом (кириллица в CP1251) в SPEC писать нельзя — latin-1 их не совпадёт. Подбирай якорь из ASCII-части строки.

Запускай с `python3 -I`, сам скрипт держи в scratchpad, а не рядом с файлами пользователя.

### 4. Записать
- `device_commit_files` со `stagedPath` из новой уникальной папки и `expectedMtimeMs` из **последнего** stage этого файла.
- `rejected` с расхождением mtime → пользователь поменял файл: stage заново, повтори шаги 1–3, не используй `force`.

### 5. Проверить запись — до того, как сообщить об успехе
- `device_list_dir`: размер файла должен совпасть с `wc -c` твоей версии.
- Для важного — `device_stage_files` ещё раз и `cmp <твоя версия> <staged>`.
- Не совпало → запись не удалась, хотя ответ был `written`. Скопируй свою версию в ещё один новый путь, закоммить заново и проверь снова.
- Только после совпадения пиши пользователю «внёс». Если проверить не удалось — так и скажи.

## Проверка смысла правок без полной сборки
- Если проект нельзя собрать в облаке, проверь что можно: синтаксис на заглушках хостовым компилятором, ассемблер/размеры структур через `clang --target=...`.
- В отчёте явно раздели «проверено» и «не проверено (нужна твоя сборка)».

## Отчёт пользователю
Коротко: какие файлы изменены и что именно в каждом, что подтверждено проверкой после записи, что осталось вне доступа и требует его действий. Если обнаружил, что прошлая запись не дошла, скажи об этом прямо и перечисли, что исправил.
